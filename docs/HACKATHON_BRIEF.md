# Revenue Guardian — Technical Brief

## The problem

When a payment provider, bank or method degrades, merchants lose revenue in two ways: payments fail, and
the usual response (blind retries) hammers the degraded path and annoys customers. Merchants rarely know
*what* is failing, *which* in-flight payments are at risk, or whether a recovery action actually brought
money back.

## What Revenue Guardian does

It turns a live stream of payment webhooks into closed-loop recovery:

1. **Detect**: 5-minute health windows per segment, compared with the same windows in earlier weeks;
   threshold and Z-score evidence; hysteresis so one bad window never opens an incident.
2. **Diagnose**: root-cause analysis decomposes excess failures by bank, method, wallet or currency, or
   declares the outage SYSTEMIC, and refuses to name a "cause" that covers the whole population.
3. **Predict**: a point-in-time failure probability for each in-flight payment, using only data known at
   that moment.
4. **Decide**: hard safety gates, then a cost/benefit choice among recovery routes that fit the
   diagnosis; ACT, MONITOR or NO_ACTION are all recorded with their reasons.
5. **Recover**: execute the route (real PayPal sandbox checkouts for link/switch routes, a clearly
   labelled simulator for gateway-side routes).
6. **Verify and attribute**: observe the real outcome from provider events, then attribute recovered
   revenue conservatively.

## Architecture in one paragraph

One FastAPI service over PostgreSQL. Signed Razorpay and PayPal webhooks are verified, deduplicated and
stored with a pipeline-run row in the same transaction (transactional outbox). A background task, backed
by a reconciler with leases, runs eight stages; every stage writes append-only, versioned records keyed
by payment attempt and provider, linked by composite foreign keys. Razorpay and PayPal have separate
analytics scopes, so one provider's traffic never moves another's baselines or incidents. Details:
[ARCHITECTURE.md](ARCHITECTURE.md).

## What makes the recovery different: customer-approved payment switching

When the diagnosis says the customer's *payment method* is failing (for example cards), retrying the
same method does not help. Revenue Guardian can instead **offer the customer a PayPal checkout** as an
alternative method:

- the offer is created only for an ACT decision whose diagnosis justifies it, only in the PayPal sandbox,
  and only for a customer not already paying with PayPal;
- the customer must approve the checkout at PayPal; the engine never captures, charges or switches
  anything, and the merchant performs the capture;
- every offer has a lifecycle (offered, accepted, declined, expired, abandoned, completed, failed) with
  deadlines and an append-only audit trail linking the original payment, diagnosis, decision, offer,
  customer response, checkout order and final outcome.

## How it avoids duplicate charges and false attribution

- **Idempotency everywhere**: provider event ids deduplicate webhooks; one command per decision; PayPal's
  `PayPal-Request-Id` is the command key, so retries return the same checkout; one offer per command and
  per checkout order; pipeline replays write nothing new.
- **Terminal states are final**: an expired, declined or completed offer never accepts another event; its
  checkout link is withdrawn from every API.
- **Double-payment awareness**: if both the original payment and a recovery checkout capture, the
  observation records the conflict.
- **Revenue only after verified payment**: an offer or a checkout is never revenue. Recovery counts only
  when PayPal's signature-verified capture of the exact offered amount arrives after the customer's
  acceptance; payments completed without the offer are not credited to it.
- **Two different numbers**: *estimated protected GMV* (a risk-weighted counterfactual estimate,
  discounted for synthetic models and weak evidence) is always shown apart from *verified recovered
  payments* (money PayPal actually captured through a real recovery).

## What is real, simulated or generated

| | Status |
|---|---|
| Razorpay and PayPal webhook verification, dedup, durable processing | real code; verified with signed test webhooks |
| Stages 2-4 detection and RCA, Stage 5 prediction, Stage 6 decisioning, gates | real; deterministic and tested |
| Stage 5 model | a transparent heuristic (not trained on real outcomes); attribution discounts it accordingly |
| Gateway retry, circuit bypass, retry backoff execution | **simulated** (`SIMULATOR_V1`, labelled everywhere): no gateway exposes these actions here |
| PayPal checkout links and switch offers | real PayPal Orders v2 sandbox code; verified against PayPal's documented responses with its HTTP API replaced in-process; **not yet run against the real sandbox** (no credentials configured) |
| Demo traffic | generated by the demo and labelled as such |
| Protected GMV | an estimate; verified recovered money is reported separately |

## Evidence

- Five-scenario demo in about 10 seconds: `./scripts/run_demo.sh` ([DEMO.md](DEMO.md)).
- Automated suites: offline unit/boundary, PostgreSQL integration/API with end-to-end scenarios,
  migration round trips with exact schema and data equality, and frontend tests ([SETUP.md](SETUP.md)).
- Safety: sandbox-only and consent rules are enforced in code *and* database constraints; tests and the
  demo refuse any database but the disposable one.

## Known limitations

- No real PayPal sandbox call has been made yet (needs credentials, a public webhook URL and a sandbox
  buyer; see [PAYPAL_SANDBOX_SETUP.md](PAYPAL_SANDBOX_SETUP.md)).
- Gateway-side routes have no real executor.
- The Stage 5 model is a heuristic; no model is validated on production outcomes.
- Under the default policy the circuit bypass outscores the PayPal switch for most payment sizes; the switch
  is chosen for very small payments or for merchants that disable the bypass (`RECOVERY_DISABLED_ROUTES`).
- INR payments are never offered a PayPal switch (PayPal INR outcomes cannot be verified here).
- Switch offers are not delivered to customers by this service; a merchant channel presents them.
- Offer deadlines are enforced by a cron script (and by any later event).
